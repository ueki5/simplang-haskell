# fnの仮引数・戻り値型注釈の省略と型推論の導入における設計上の考慮点

`docs/step014.md`で`let`文の型注釈が省略可能になった。同ドキュメントの「明示的なスコープ外」節では、`fn`の仮引数・戻り値型の注釈省略は「呼び出し規約・スタックスロット割り付けが宣言順に依存するため、別途の設計を要する」として明示的に見送られていた。今回はこの`fn`の仮引数型・戻り値型についても注釈省略と型推論を導入する。

`let`と異なり、パラメータには「初期化式」が無いため、型の根拠は (a) 戻り値型なら自身の`return`文・末尾式、(b) パラメータ型なら**呼び出し側の実引数式**からしか得られない。この結果、型が複数の関数にまたがって依存し合い、自己再帰・相互再帰による循環が生じ得る。本ステップでは、こうした循環（型未確定な項目同士が互いを経由してしか解決できない状態）を検出したらコンパイルエラーとする方針を採る。ただし、`fact`のような通常の自己再帰・`is_even`/`is_odd`のような通常の相互再帰まで一律にエラーとしてしまっては実用に耐えないため、「自分自身の解決を、自分自身の情報だけを根拠に行おうとする」経路は循環として扱わない（詳細は2.3節）。

## 0. 方針として確定した事項

| 項目 | 決定内容 |
|---|---|
| 追加する構文 | `fn`の仮引数の型注釈`': type'`、および戻り値の型注釈`'-> type'`をそれぞれ独立に省略可能にする（例: `fn add(a, b) { a + b }`、`fn add(a: i64, b) -> i64 { a + b }`のような混在も可） |
| パラメータ型の推論元 | そのパラメータの位置に渡された、プログラム全体のあらゆる呼び出し箇所の実引数式（プログラム中の全fn本体＋暗黙main文・末尾式を対象に走査する） |
| 戻り値型の推論元 | その関数自身の`return`文の式・末尾式（`let`の`SLetInferred`と同様、既存の`inferMaybeType`と同じ規則で単一化する） |
| 循環時の扱い | 型未確定なスロット同士が互いにしか依存できない場合はコンパイルエラーとする（明示的な型注釈で断ち切るようメッセージで促す）。ただし通常の自己再帰・相互再帰（返り値/引数の少なくとも一方に外部からの手がかりがある場合）は循環として扱わない |
| デフォルト規則 | 呼び出し箇所・return/末尾式のいずれからも情報が得られないスロットは、既存の`inferType`と同じく`i64`をデフォルトとする |
| 宣言順依存性 | 無し。呼び出し側・呼び出される側のどちらが先に書かれていても、循環にならない限り解決できる |
| 呼び出し先本体の使われ方 | パラメータ型の推論には使わない（CLAUDE.mdの「ボトムアップ型推論は不要」という既存方針を維持する） |

## 1. AST・文法の変更

`data FnDecl = FnDecl String [(String, Type)] Type Body`を

```haskell
data FnDecl = FnDecl String [(String, Maybe Type)] (Maybe Type) Body
```

に変更する。`let`の`SLet`/`SLetInferred`のような並行コンストラクタ方式は、パラメータごとの省略・非省略の組み合わせが指数的に爆発するため採らず、フィールドを直接`Maybe Type`にする（`fn`は`test/Spec.hs`内で`FnDecl`を直接パターンマッチする箇所が8箇所のみと少なく、`Just`で包むだけの機械的な修正で済むため影響は限定的）。

パーサーは`let`の`parseLetStmt`と同じ1トークン先読みパターンを使う。仮引数は識別子の直後が`':'`かどうかで分岐し（`parseParam`）、戻り値型は仮引数リストの直後が`'->'`かどうかで分岐する（`parseFnDecl`）。

```
fn-decl ::= 'fn' IDENT '(' (IDENT (':' type)? (',' IDENT (':' type)?)*)? ')' ('->' type)? '{' stmt* expr '}'
```

## 2. シグネチャ解決アルゴリズム

`compile`の最初の1パス目（旧`buildFnSigs`）を、`resolveFnSigs :: [FnDecl] -> [Stmt] -> Expr -> Either String FnSigs`に置き換える。最終的な`FnSigs = Map String ([Type], Type)`の形は変わらず、**それより後段のパイプライン（`compileProgram`/`compileFnDecl`/`compileExprTyped`/`compileStmtsFrom`/`allocParams`/codegen/VM）は一切変更していない**。`compileFnDecl`だけは、`FnDecl`自身のフィールドが`Maybe Type`になったことに伴い、具体的な型を`FnDecl`からではなく確定済みの`fnSigs Map.! name`から取得するよう修正した（`params`は名前のみ`FnDecl`から、型は`fnSigs`から得て`zip`する）。

### 2.1 スロットと証拠

型注釈が省略された箇所1つを`Slot`（`ParamSlot 関数名 引数番号 | ReturnSlot 関数名`）として表す。`main`予約名・重複定義・最大6引数の構造検証は型の中身を見ずに行える（旧`buildFnSigs`のロジックをそのまま`validateFnShapes`として踏襲）。

パラメータ・戻り値の型注釈が省略された箇所すべてを未解決`Slot`として列挙し、それ以外（型注釈済み）は最初から`ResolvedSlots`（`Map Slot Type`）へ投入する。

プログラム全体（全fn本体＋暗黙main文・末尾式）を1回走査し、次の2種類の証拠（`Evidence = [(Slot, Either Slot (Maybe Type))]`）を集める（`programEvidence`/`collectEvidenceStmts`/`callEvidence`。`compileStmtsFrom`と同じ形でスコープをpush/popしながら辿る）:

- 式ツリー中のあらゆる位置に現れる`Call name args`ノードについて、各実引数式`args !! i`の型を`(ParamSlot name i, ...)`の証拠として記録する
- 関数自身の`return`文の式・末尾式の型を`(ReturnSlot 関数名, ...)`の証拠として記録する

各式の型は`resolveExprType`（`inferMaybeType`のLocalEnv版。変数参照・呼び出しがまだ解決されていないスロットを指していれば、確定的な型エラーではなく「そのスロット待ち」として結果を返す点だけが`inferMaybeType`と異なり、それ以外の構造は完全に同一）で求める。

### 2.2 固定点ループ

未解決スロットが残っている間、証拠を**現在の`ResolvedSlots`に対して**取り直しながら次を繰り返す（`resolveSlots`）:

- 各未解決スロットについて、集まった証拠のうち他の未解決スロット待ちのものが1つでもあれば、そのスロットは今回は解決を見送る
- 全ての証拠が具体的な型（または「情報なし」）であれば、既存の`unifyMaybeType`/`unifyType`で単一化する（型が矛盾すれば、そのまま`"type mismatch: X and Y"`が伝播する）。証拠が1つも無ければ`unifyMaybeType`は`Nothing`を返し、既存の`inferType`と同じ規則で`i64`にデフォルトする
- 1ラウンドで1つも前進しなければ、残りは（後述の自己ループを除いて）互いに依存し合う循環と判定し、`"circular type inference: ..."`エラーを返す

### 2.3 自己ループの許容（この設計の要）

あるスロット`S`向けの証拠が「`S`自身待ち」だった場合、それは無視する（依存関係として数えない）。これが無いと、たとえば

```
fn fact(n) {
if n <= 1 { return 1; }
n * fact(n - 1)
}
fact(10)
```

のような**通常の**自己再帰でパラメータ型を省略しただけで「循環」と誤検出してしまう（`fact`自身の呼び出しの引数`n - 1`は`fact`の`ParamSlot`自身を参照するが、外部の呼び出し`fact(10)`から得られる証拠だけで十分解決できるべきである）。`n`の型は外部呼び出しから即座に`i64`へ解決され、その後`fact`の戻り値型は`return 1;`（無型リテラル、`i64`にデフォルト）から解決される。呼び出される関数の本体内での**パラメータの使われ方**そのものからの推論（ボトムアップ推論）は行わない — パラメータ型の唯一の証拠源は常に呼び出し側の実引数式である。

一方、`S`以外の**別の**未解決スロット待ちの証拠は正当な依存関係として扱う。たとえば外部からの手がかりが全く無い相互再帰

```
fn a(x) -> i64 { b(x) }
fn b(y) -> i64 { a(y) }
42
```

は、`ParamSlot a 0`が`ParamSlot b 0`に、`ParamSlot b 0`が`ParamSlot a 0`に、互いに依存したまま前進不可能になり、循環としてエラーになる。

## 3. コード生成への影響

無し。`resolveFnSigs`が返す`FnSigs`はこれまでと全く同じ形（`Map String ([Type], Type)`、値は全て具体的な`Type`）であり、`compileFnDecl`以降は型注釈が省略されていたかどうかを一切区別しない。

## 4. `docs/step009.md`/`docs/step014.md`からの変更点まとめ

| ファイル / 項目 | step014まで | step015での変更 |
|---|---|---|
| `FnDecl` | `FnDecl String [(String, Type)] Type Body` | `FnDecl String [(String, Maybe Type)] (Maybe Type) Body` |
| `parseParam` / `parseFnDecl` | `':' type`・`'->' type`必須 | それぞれ1トークン先読みで省略可能に |
| `buildFnSigs` | 構造検証のみ行い、型はFnDeclからそのまま集める | `resolveFnSigs`に置き換え。構造検証（`validateFnShapes`）はそのまま踏襲した上で、省略された型を呼び出し箇所の実引数・自身のreturn/末尾式から解決する固定点ループを追加 |
| `compileFnDecl` | `FnDecl`自身の`params`/`retTy`を直接使用 | 具体的な型は`fnSigs Map.! name`から取得（`FnDecl`のフィールドは`Maybe Type`になったため） |
| `inferMaybeType`等 | 変更なし | 変更なし（`resolveExprType`はこれらとは別の新規関数として追加し、既存関数は再利用のみ） |

## 5. 明示的なスコープ外

- 呼び出される関数の本体内でのパラメータの使われ方からの推論（ボトムアップ推論）は採用しない。パラメータ型の証拠は常に呼び出し側の実引数式のみ
- 循環依存の自動解決（fixpointを超えた特殊なアルゴリズムでの循環の巻き戻し等）は行わない。循環は常に明示的な型注釈の追加をユーザーに促すエラーとする

## 6. テストへの影響

- Parser: パラメータ型省略・戻り値型省略・両方省略・パラメータごとの混在省略がそれぞれ正しく`Nothing`としてパースされること
- 意味論（compile）: 呼び出されない省略パラメータの`i64`デフォルト、複数呼び出し箇所の型一致による成功、複数呼び出し箇所の型不一致によるエラー、外部からの手がかりが無い純粋な自己再帰の成功（循環にならないことの確認）、相互再帰（パラメータ省略・戻り値省略それぞれ）で外部からの手がかりが無い場合の循環エラー、恒等関数パターン・ポインタ引数からの推論
- Integration: パラメータ・戻り値の型注釈を省略した関数（`add`・自己再帰する`fact`・恒等関数`id`）をgccでコンパイル・実行し、期待する数値を出力すること
