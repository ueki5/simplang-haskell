# 値を返すブロック（ブロック式）における設計上の考慮点

step005 で導入したブロック `{ ... }` は、変数のスコープを作るだけの文で、値を返さなかった。そのため、一時変数のスコープを絞りながら値を作る書き方（`let y = { let t = x + 1; t * t };`）ができなかった（backlog「値を返すブロック・`if`・`while`」）。

今回、**ブロックを式にする**。値はブロックの末尾式で、型は末尾式の型になる。値を返す `if`・`while` は次の step 以降に回す。

```
fn main() -> i64 {
    let x = 3;
    let y = {
        let t = x + 1;
        t * t
    };                          // y = 16。t はここで見えなくなる
    y + { let z = 2; z * 10 }   // 16 + 20
}
```

```
$ simplang-haskell main.sl -o prog && ./prog
36
```

## 0. 方針として確定した事項

| 項目 | 決定内容 |
|---|---|
| 構文 | `{ stmt* expr? }` を式（primary）として書ける。値は末尾式で、省略すると `()`（fn 本体と同じ） |
| 型 | ブロックの型は末尾式の型。期待型はそのまま末尾式へ伝播する |
| スコープ | 従来どおり新しいスコープを作る。中で宣言した変数は外から見えない |
| 文の位置のブロック | Rust と同じく、文の途中に置いたブロックの値は `()` でなければならない（`{ 1 } let y = 2;` は型エラー）。ブロックの**最後**に置いたブロックは、外側のブロックの末尾式になる |
| if / while の本体 | Rust と同じくブロック（文の列＋末尾式）として読み、末尾式は `()` でなければならない（`if c { 1 }` は型エラー。従来はパースエラー） |
| `{ ... };` | 従来どおりエラー（空文が無いため） |
| break / continue / return | ブロック式の中でも使える。式の途中で抜けても、操作スタックに残った値を正しく捨てる |
| 定数式 | ブロックは書けない |

## 1. 考慮点

### 1.1 文の位置のブロックと末尾式の区別

`{` で始まる文は、従来はすべてブロック文だった。ブロック式を入れると、fn 本体の最後のブロックが末尾式なのか文なのかを決める必要がある。

```
fn f() -> i64 {
    let a = 1;
    { a + 1 }       // 末尾式（f の戻り値）
}
```

Rust と同じく、**後ろに `}` が続くブロックは末尾式、それ以外は文**とする。文として置いたブロックの値は `()` でなければならない。`{ 1 } let y = 2;` は Rust でも `expected (), found integer` になる。値を捨てる式文 `{ 1 };` にはしない（空文が無いので、`;` は従来どおりパースエラー）。

`{ 1 } + 2` を文の先頭に書いた場合は、Rust と同じく `{ 1 }` で文が終わり、`+ 2` がパースエラーになる。

パーサは、文の列を読む `parseStmts` が `{` を見たらブロックを読み、直後が `}` なら「文は無い」として元のトークン列のまま戻る。外側（fn 本体・ブロック）が改めて末尾式として読む。これは、`a[0]` や `*p` の末尾式を試し読みしてから読み直す既存のやり方と同じである。

### 1.2 if / while の本体もブロックとして読む

1.1 の規則では、if の本体の最後にブロックを置くと（`if c { { ... } }`）、それが末尾式として読まれる。しかし従来の if/while の本体は文の列だけで、末尾式が無いため `}` を期待してエラーになる。

| 選択肢 | 評価 |
|---|---|
| 本体の中だけ、最後のブロックも文として扱う | `parseStmts` に「末尾式を許すか」の引数が要る。ブロックの読み方が場所で変わる |
| **本体もブロック（文の列＋末尾式）にする（採用）** | Rust と同じ。末尾式は `()` でなければならないので、`if c { 1 }` は `expected (), found integer literal` の型エラーになる。fn 本体・ブロック式・if/while の本体を同じ関数 `parseBlockBody` で読める。値を返す if を入れるときは、末尾式の期待型を `()` から変えればよい |

### 1.3 条件式の後の `{` との衝突

`if x { ... }` の `x` の後の `{` が、ブロック式として読まれることは無い。primary としての `{` は、式の先頭か二項演算子・前置の単項演算子の直後でしか読まれず、`x` の後は後置演算子（`[`、`.`）しか見ないためである。`if { c } { ... }` のように条件の先頭に書いたブロックは条件式になる（Rust と同じ）。

Rust は構造体リテラル `S { .. }` と衝突するため条件式の位置に制限を設けているが、simplang には構造体が無いので不要である。

### 1.4 式のコンパイルに文の文脈が要る

ブロック式は中に文を含むので、式のコンパイル（`compileExprTyped`）が次のものを必要とするようになる。

| 必要なもの | 理由 |
|---|---|
| cursor（スタック上の次の空き位置） | ブロック内の `let` の配置 |
| LoopCtx / ReturnCtx | ブロック内の break・continue・return |
| ラベル番号（`CompileM` の状態） | ブロック内の if・while |

そこで、`FnSigs`・`Env`・cursor・`LoopCtx`・`ReturnCtx` をレコード `Ctx` にまとめ、`compileExprTyped :: Ctx -> Type -> Expr -> CompileM [Instr]` にする。文のコンパイル（`compileStmtsFrom`・`compileIf`・`compileWhile`）も同じ `Ctx` を受け取る。従来は5つの引数を個別に渡していたため、`Ctx` にまとめると引数の追加が1か所で済む。

型推論（`inferMaybeType`）は従来どおり `FnSigs -> Env` の純粋な関数に保つ。ブロック `{ stmts; t }` の型は、ブロック内の宣言だけをたどった Env（`blockEnv`。`let x: T` は `T`、`let x = e` は `e` の推論型）で末尾式 `t` を推論して求める。推論が `&e` で `addressOf`（命令列を作る関数）を使っていたのは、型だけを求める `placeType` に分ける。

定数式の評価（`evalConstExpr`）は、ブロックを `checkConstExpr` で拒否してから `compileExprTyped` を呼ぶので、ラベル番号は使われない。

### 1.5 ブロック内の変数の配置

ブロック内の変数は、従来のブロック文と同じく cursor から下へ詰めて置き、ブロックを抜ければ領域を再利用する。式の中に置いたときは、どこを cursor にするかが問題になる。

```
let a = [{ let p = 1; let q = 2; p + q }, 10, { let r = 3; let s = 4; let t = 5; r + s + t }];
```

配列の `let` は要素を1つずつ評価して、`a` の領域へストアする。`let` の cursor（`a` の領域の上端）をそのままブロックに渡すと、3つ目の要素のブロックの `t` が、ストア済みの1つ目の要素と同じ位置に置かれて壊してしまう。

そこで、**`let` の初期化式は、宣言する変数の領域の下端を cursor にしてコンパイルする**。ブロック内の変数は宣言中の変数より下に置かれ、ストア済みの要素とは重ならない。それ以外の位置（代入の右辺・実引数など）では、生きている変数はすべて cursor より上にあるので、文の cursor をそのまま使えばよい。

### 1.6 式の途中での制御の移動

従来の if・while は文の境界にしか現れず、そこでは操作スタックが常に空だった。コード生成の `genBody` はこれを前提に、操作スタックの深さを命令列の先頭から線形に数えて、関数呼び出しの直前のパディング（16バイト境界への調整）を決めていた。ブロック式では、値が積まれた状態で if・while・break などが実行されるようになる。

```
while i < 10 {
    let y = 100 + { if i == 3 { break; } i };
    i = i + 1;
}
```

```
Push 100          ← 操作スタック：[100]
  ...i == 3...
  JmpIfZero
  Jmp while_end   ← break：100 を積んだままループの外へ飛ぶ
  Label ..
  Load i          ← [100, i]
IAdd
```

問題は2つある。

1. **break・continue で値が残る**：`100` を積んだまま `while_end` へ飛ぶので、ループの外で操作スタックに `100` が余る。break・continue のジャンプは、**飛び先のラベルの深さまで操作スタックを捨ててから飛ぶ**必要がある。これを新しい中間命令 `JmpDrop L` で表し、codegen は `addq $8×余分, %rsp; jmp L` を出す
2. **線形に数えた深さが合わない**：無条件ジャンプの後ろのコードは、そのジャンプを通らない経路からしか実行されない。それを同じ流れとして数えると、ラベルの位置の深さを誤る

2 は、実は従来から `return` で起きていた。

```
if c { return 1; }
g()
```

`return 1` は `Push 1; Jmp fn_end` になる。線形に数えると `1` が積まれたまま if の後ろへ続くとみなすので、`g()` の呼び出しで不要なパディングを入れていた。simplang の関数は16バイト境界を要求する命令を使わないので、表に出ていなかった。

そこで `genBody` を2パスにする。

1. **ラベルの深さを求める**：命令列を前から順にたどる。無条件ジャンプ（`Jmp`・`JmpDrop`）の後は到達不能として深さを「不明」にする。ラベルでは、フォールスルーの深さを採り、フォールスルーが不明なら、それより前に現れた `Jmp`/`JmpIfZero` の深さを採る
2. **生成**：ラベルの位置で深さを 1 の値に置き直し、`JmpDrop` では現在の深さとラベルの深さの差だけ捨てる

`JmpDrop` は、飛び先の深さを決める根拠には使わない（捨てた後の深さは飛び先の深さそのものなので）。break の飛び先 `while_end` には、必ず条件の `JmpIfZero` が先に現れ、continue の飛び先 `while_start` は break より前にフォールスルーで現れるので、深さは必ず決まる。

**return は `Jmp` のまま**とする。return は値を積んで fn 末尾へ飛ぶので、`JmpDrop` のように上から捨てると値が消えてしまう。余分な値は値の下に残るが、fn 末尾のエピローグは戻り値を上から取り出し（`popq`。スライスは2つ）、`leave` でスタックを関数の入口の状態へ戻すので、害にならない。

| 選択肢 | 評価 |
|---|---|
| 文の境界でない位置での break/continue/return を禁止する | コンパイラは操作スタックの深さを知らないので、「式のどこにあるか」を引数で持ち回る必要がある。Rust でも書ける（`let x = { if c { break; } 1 };`） |
| すべての `Jmp` で飛び先の深さまで捨てる | return の値を捨ててしまう。return だけ値を退避して捨て直す特別扱いが要る |
| **break/continue だけ `JmpDrop` にする（採用）** | 余分な値が問題になるのは break/continue だけで、それを命令の種類で明示できる |

### 1.7 ダングリングポインタの簡易検査

fn の末尾式・return・static への代入の右辺が直接 `&ローカル` である形を検出する `isLocalRef` は、ブロックの末尾式もたどる。ブロック内の変数も `blockEnv` でローカル変数として見えるので、次の2つを検出する。

```
fn f() -> &i64 { let x = 1; { &x } }    // cannot return reference to local variable: x
fn g() -> &i64 { { let y = 1; &y } }    // cannot return reference to local variable: y
```

`let p = { let y = 1; &y };` のように、ブロックの外の変数へ持ち出す形は検出しない。従来の「ブロックを抜けたあとの `&local` の使用」（backlog 1.5）と同じ問題である。

## 2. 構文・AST

```
block      ::= '{' stmt* expr? '}'           （末尾式の省略は () とする）
fn-decl    ::= 'fn' IDENT '(' params? ')' ('->' type)? block
block-stmt ::= block                          （直後が '}' でない位置。値は () でなければならない）
if-stmt    ::= 'if' expr block ('else' 'if' expr block)* ('else' block)?
while-stmt ::= 'while' expr block
primary    ::= ... | block
```

| AST | 変更 |
|---|---|
| `Expr` | `Block Body` を追加 |
| `SBlock` | `SBlock [Stmt]` → `SBlock Body` |
| `SIf` | `SIf [(Expr, [Stmt])] (Maybe [Stmt])` → `SIf [(Expr, Body)] (Maybe Body)` |
| `SWhile` | `SWhile Expr [Stmt]` → `SWhile Expr Body` |

`Body = ([Stmt], Expr)` は fn 本体と同じ型で、`parseBlockBody`（`{` の直後から `}` までを読む）で共用する。

## 3. 意味論

- `Block (stmts, t)`：新しいスコープで `stmts` をコンパイルし、その Env と cursor で `t` を期待型でコンパイルする。値は `t` の値
- `SBlock`・if/while の本体：文の列をコンパイルし、末尾式を期待型 `()` でコンパイルして `IPop` で捨てる。末尾式が `UnitLit` なら命令を出さない（値 0 を積んで捨てるだけなので）
- 期待型が `&[T]` で、ブロックの型が `&[T; N]` なら、従来の式と同じく `&[T]` へ変換する（`compileExprTyped` の入口の変換が、`inferMaybeType` によるブロックの型で働く）
- 配列を値として返すブロック（`let a = { [1, 2] };`）は、配列が値として使えないのでエラー

| ケース | メッセージ |
|---|---|
| 文の途中のブロックの値が `()` でない（`{ 1 } let y = 2;`） | `type mismatch: expected (), found integer literal` |
| if/while の本体の末尾式が `()` でない（`if c { x }`、x: i64） | `type mismatch: expected (), found i64` |
| ブロックの値と期待型の不一致（`let x: i32 = { 1i64 };`） | `type mismatch: expected i32, found i64` |
| ブロック内の変数をブロックの外で使う | `undeclared variable: t` |
| 定数式にブロック | `initializer of N is not a constant expression` |

## 4. コード生成

| 命令 | 生成するコード | 深さの増減 |
|---|---|---|
| `JmpDrop L`（新規） | 余分 k = 現在の深さ − L の深さが正なら `addq $8k, %rsp`、続けて `jmp L` | 0（後ろは到達不能） |

- `genBody` を 1.6 の2パスにする。ラベルの深さは `Map String Int` で持つ
- break/continue は `Jmp` の代わりに `JmpDrop` を出す。return・if/while の内部のジャンプは `Jmp` のまま
- VM（`run`）は `Jmp` と同じく `JmpDrop` を扱わない

## 5. 移行

- `SBlock`・`SIf`・`SWhile` の AST を直接書いているテスト（parse の12件）を `Body` の形へ書き換える。`{ { } }` の内側のブロックは、外側のブロックの末尾式 `Block` になる
- break/continue の命令列を比べている既存のテストは無かった
- 従来のプログラムの意味は変わらない。生成コードは、break/continue（`JmpDrop` で余分が無ければ `jmp` のみ）と、return の後の関数呼び出しのパディング（1.6 の不具合の修正）だけが変わる
- `docs/language.md`：文法（block）、式（ブロック式）、文（if/while の本体、文の位置のブロック）、スコープ
- `docs/architecture.md`：AST・`Instr`・`Ctx`、パーサの文の判別、型検査（`blockEnv`・`placeType`・ブロック内の配置）、コード生成のアライメント
- `docs/backlog.md`：該当行を「値を返す `if`・`while`（`loop`）」に縮め、ブロックを実現済みへ移す
- サンプル：`sample/samp036-0.sl`（冒頭の例）を追加する。既存のサンプルへの影響はない

## 6. スコープ外（将来の課題）

| 課題 | 補足 |
|---|---|
| 値を返す `if`・`while`／`loop` | 本体はブロックとして読むようになったので、末尾式の期待型を `()` から変え、分岐の合流点で値を受け渡せばよい。合流点の深さは 1.6 のラベルの深さで扱える |
| 発散型 `!` | `{ return 1; }` の型は今回も末尾式 `()` |
| ブロックの外へ持ち出した `&local` の検出（`let p = { let y = 1; &y };`） | backlog「ブロックを抜けたあとの `&local` の使用」と同じ |
| 配列を値として返すブロック | backlog「配列のコピー・比較」「配列の値返し」と同じく、配列を値として扱う仕組みが要る |
