# 変数・代入の導入における設計上の考慮点

現在の実装（単一の算術式 → 1つの `printf`）を、変数・代入をサポートする形に拡張する際に効いてくる設計ポイントを、パイプラインの各段階ごとに整理する。

## 0. 方針として確定した事項

以下は今回の要件定義で確定した。旧版で未決定事項としていた (A) 代入を式/文どちらにするか、(B) 変数をスタック/グローバルどちらに置くかに加え、前回持ち越した §7 の4項目も今回すべて解消済み。

| 項目 | 決定内容 |
|---|---|
| 識別子 | 英大小文字で開始し、以降は英大小文字・数字・`_` の0文字以上 |
| 変数宣言 | `let 変数名: 型 = Expr;`（型は現状 `i64` のみ、初期化は必須） |
| 代入 | `変数名 = Expr;`。**式ではなく文（Stmt）** として扱う |
| 文の区切り | 各文の末尾に `;` を必須とする |
| 末尾の式 | プログラム末尾に `Expr` を必ず1つ置く。この場合は `;` を付けない |
| 文だけで終わるプログラム | 末尾に `Expr` が無い場合はコンパイルエラー |
| 変数の再宣言 | 同名変数への2回目の `let` はコンパイルエラー |
| 未宣言変数の使用 | 代入・式中の参照のどちらもコンパイルエラー |
| 変数参照 | `Expr` に `Var String` を追加し、宣言・代入の右辺や末尾式で変数を読み出せる |
| 変数の実体 | `%rbp` 相対のスタックローカル変数 |

## 1. 文法・構文（Lexer / Parser）

- **トークン追加**: `TIdent String`（識別子）、`TLet`（予約語 `let`）、`TColon`（`:`）、`TAssign`（`=`）、`TSemicolon`（`;`）
  - 型名 `i64` は専用トークンを増やさず `TIdent "i64"` として字句解析し、パーサ側で「`i64` 以外はエラー」と検査すれば十分（型が1種類しかない今の段階で型トークンを増やすのはオーバースペック）。
  - 識別子スキャン時に予約語 `let` かどうかを判定し、`TLet` / `TIdent` を出し分ける。
- **Program の構造化**: `parse :: [Token] -> Either String Expr` を、`Program = ([Stmt], Expr)`（文の列 + 必須の末尾式）を返す形に変更する。
  ```haskell
  data Stmt = SLet String Expr | SAssign String Expr
  ```
  型注釈（`: i64`）はパース時に検証するのみで、AST には保持しない（型が1種類のみのため情報として不要）。
- **文と末尾式の判別**: 文の並びをループでパースし、各ステップで次のように分岐する。
  - 先頭が `TLet` → let文としてパース
  - 先頭が `TIdent name` かつ次が `TAssign` → 代入文としてパース
  - それ以外 → 文の列はここで終了。残りを末尾の `Expr` としてパースする
  - 2トークン先読みがこの1箇所だけで済むため、既存の再帰下降パーサ構造への影響は小さい。
  - 末尾 `Expr` のパースは省略不可とする。トークンが尽きている、あるいは式として解釈できない場合はそのままエラーとして伝播すればよく、「省略時はOK」という特別扱いを入れる必要がないため実装はむしろ単純になる。
- **`Expr` への変数参照追加**: `let`/代入の右辺や末尾式で変数を読み出せる必要があるため、`Expr` に `Var String` を追加し、`parseFactor` に識別子ケースを足す（現状は `TInt` / `TLParen` / `TMinus` のみ）。

## 2. 意味論

- **宣言チェック**: 変数集合（`Set String` で十分、型は1種類なので型情報は持たなくてよい）をパイプラインに引き回し、
  - `let` で同名の変数が既に存在する場合はコンパイルエラー（現時点ではブロックスコープがなく再宣言＝シャドーイングの概念がないため）
  - 代入・変数参照で未宣言の変数が使われた場合はコンパイルエラー
- **初期化漏れは構文上発生しない**: 宣言時の初期化を文法上必須にしたため、「未初期化変数」への対処は不要（旧版の懸念点は解消）。
- **プログラムの出力**: 末尾の `Expr` は必須のため、プログラムは常にちょうど1つの値を `printf` する（現行の「式1つ→printf1回」という出力モデルをそのまま維持できる）。文だけで終わる（末尾 `Expr` なし）プログラムは構文上受理せず、コンパイルエラーとする。

## 3. IR（`Instr`）とコンパイラ

- `Instr` に `Load Int` / `Store Int` を追加。Int は変数ごとに一意な `%rbp` 相対オフセット（バイト単位、解決済み）とする。
- `compile` は左から右への単一パスで環境（`Map String Int`：変数名→オフセット）を引き回せる。文法上「宣言 → 代入・参照」の順序が強制される（前方参照不可）ため、事前に変数を数え上げるプレパスは不要。
- オフセット割り当ては `let` 出現順に `-8, -16, -24, ...` を割り振ればよい（`i64` は全て8バイト固定なので配置計算は単純）。

## 4. コード生成（メモリ配置・スタックフレーム）

- **フレームサイズの決定**: `compile` が出力する `Load`/`Store` はすでに解決済みオフセットを持つので、`codegen` 側は命令列中の最大オフセットをスキャンして必要なフレームサイズを求め、プロローグで一度だけ `subq $N, %rsp` すればよい（`compile` からフレームサイズを別途受け渡す必要がない）。
- **エピローグは `leave` 相当にする**: 現行の `popq %rbp` は「pushとpopの数が対応している」前提に依存しているが、ローカル変数用に確保した領域はpushで積んだものではないため単純なpopでは辻褄が合わない。`movq %rbp, %rsp; popq %rbp`（= `leave` 命令）に変更し、確保量によらず正しく巻き戻す。
- **16バイトアライメント**: プロローグ直後（`push %rbp` 完了時点）で `%rsp` は16バイト境界に揃っている、という既存コードの前提がある。ここから `subq $N,%rsp` で変数領域を確保すると、Nが8の倍数かどうかでその後の境界がずれる可能性がある。対策として、`call printf` / `call exit` の直前に `andq $-16, %rsp` を挿入して強制的に境界を合わせるのが簡単。呼び出し直前は必要な値をすでにレジスタへ退避済み（`popq %rsi` 等）なので、`rsp` を切り下げても情報は失われない。
- **`Load`/`Store` の実コード**: `movq -8(%rbp), %rax` / `movq %rax, -8(%rbp)` のように、Push/Pop命令と組み合わせて生成する。

## 5. VM（`run`、テスト用スタックマシン）

- `go` の型を、値スタックに加えて変数領域 `Map Int Int`（オフセット→値）を引き回す形に変更する。
- `Load off` はマップから読み出し、`Store off` は書き込む。コンパイル時の宣言チェックが機能していれば「未初期化オフセットの読み出し」は原則発生しないはずだが、テストで不正な命令列を直接組み立てるケースもあるため、見つからない場合は `Left "uninitialized variable"` を返すガードを入れておく。

## 6. テストへの影響

- Tokenizer: 識別子、`let` 予約語、`:` `=` `;` の各トークン化
- Parser: `let` 宣言・代入文のパース、文と末尾式の判別、変数参照を含む式
- CodeGen: `Load`/`Store` の命令列、フレームサイズ算出、`leave`、アライメント
- Integration: `let x: i64 = 1; let y: i64 = 2; x = x + y; x` のような実プログラムをコンパイル・実行して検証
