# スロット関連の型についてのQ&A（2026-09-18）

対象: `src/Compiler.hs` の関数の仮引数・戻り値型注釈省略と型推論（`resolveFnSigs`まわり、`Compiler.hs:416-749`）。

## Q1. スロットの状態を表す型がありすぎでよくわからない。列挙して使い方をまとめてほしい

`Slot`関連の型は5つあり、「型注釈省略の推論を1パスで固定点に持っていく」ためのフェーズ用の型。

| 型 | 定義 | 役割 |
|---|---|---|
| `Slot` | `ParamSlot String Int \| ReturnSlot String` (:416) | 「どの関数の何番目のパラメータ／戻り値」という省略された型注釈1箇所を指す識別子（キー） |
| `ResolvedSlots` | `Map Slot Type` (:425) | 解決済みスロットの実際の値。固定点ループが回るたびに確定分が追加される |
| `LocalEnv` | `[Map String (Either Slot Type)]` (:429) | 関数本体走査中のローカル変数環境。`Env`と違い、まだ確定していない仮引数は`Left slot`（解決待ち）として持てる |
| `SlotResult` | `Either String (Either Slot (Maybe Type))` (:445) | 1個の式を型付けしようとした結果。`Left err`=確定エラー、`Right (Left slot)`=スロット待ちでブロック、`Right (Right mty)`=型が求まった（`Nothing`は未確定リテラルの意） |
| `Evidence` | `[(Slot, Either Slot (Maybe Type))]` (:522) | プログラム全体を1回走査して集めた「(対象スロット, その証拠)」のペアの束 |

### 使い方の流れ（`resolveFnSigs`が起点）

1. `validateFnShapes`（構造検証）
2. `initialSlots`: 注釈済みは`ResolvedSlots`へ、省略分は未解決`[Slot]`へ分類
3. `resolveSlots`が固定点ループ:
   - `programEvidence`が全関数＋暗黙mainを走査して`Evidence`を作る
     - 各関数は`fnDeclEvidence`が担当: `paramLocalScope`→`collectEvidenceStmts`（内部で`callEvidence`・`resolveExprType`を使用）
   - `resolveOne`が各未解決スロットについて、自分自身待ちの証拠を無視しつつ単一化（証拠ゼロなら`i64`にデフォルト）
   - 1ラウンドで前進がなければ循環エラー（`describeSlot`）
4. 全スロットが埋まったら`FnSigs`（通常の`Type`のみ）を組み立て、以降は`Slot`系の型は出てこない

## Q2. LocalEnvはなんで必要なのか

関数本体の中で変数(`Var`)を参照するたびに「その変数が今どんな型か」を引けないと、式の型推論(`resolveExprType`)が進められないため。

- 仮引数もletも、まだ確定した`Type`を持っているとは限らない（型注釈省略時は`ParamSlot`/自身の推論待ち）ため、値は`Type`ではなく`Either Slot Type`
- `Var`の型を引くには、ブロックのpush/pop・シャドーイングを反映したスコープ構造そのものが必要（最終コンパイル時の`Env`と同じ構造をこの推論フェーズでも再現する必要がある）
- `Env`の値`(Int, Type)`は「まだ分からない」を表現できないため、専用の`LocalEnv`が必要

## Q3. LocalEnv, SlotResult, Evidenceの３つはすべて型推論の中間状態という認識で合っているか

大枠は合っているが、性質は異なる。ラウンドをまたいで蓄積される「本当の永続状態」は`ResolvedSlots`だけで、他の3つは毎ラウンド`programEvidence`呼び出しのたびにゼロから作り直される一時的な値。

| 型 | 性質 |
|---|---|
| `ResolvedSlots` | ラウンドを跨いで蓄積される唯一の永続状態 |
| `LocalEnv` | 1回の走査中だけ生きるスレッド状態（都度作り直し） |
| `SlotResult` | 1個の式を型付けした結果（値、状態ではない） |
| `Evidence` | 1ラウンド分の`SlotResult`たちを集めた出力リスト |

## Q4. 引き回していない３つの型について、それぞれどの関数でどのように使われているか

### `LocalEnv`（1回の走査の中だけ引き回される）

- `lookupLocal`(:431) / `setLocal`(:437) — 生の読み書きプリミティブ
- `paramLocalScope`(:628) — 仮引数リストと`ResolvedSlots`から最内スコープ1枚を新規生成
- `fnDeclEvidence`(:654) — `env0`を初期化して`collectEvidenceStmts`に渡し、戻った`env1`を末尾式の`callEvidence`/`resolveExprType`に使う
- `collectEvidenceStmts`(:565) — 唯一`LocalEnv`を実際に更新しながら文を左から右へ辿る関数。`SLet`/`SLetInferred`が`setLocal`で束縛追加、`SBlock`/`SIf`/`SWhile`が`Map.empty : env`でpushし内側の結果を捨ててpop相当を実現
- `programEvidence`(:641) — 暗黙main用に`[Map.empty]`で初期化して`collectEvidenceStmts`に渡す
- `addressOfSlot`(:456) / `resolveExprType`(:470) / `callEvidence`(:526) — 読むだけで更新しない

### `SlotResult`

- `resolveExprType`(:470) — 唯一の生成元
- `chainSlot`(:448) — `resolveExprType`内部で`SlotResult`同士を連結
- `callEvidence`(:526) — 各実引数に`resolveExprType`を呼び、`ParamSlot`とペアにして`Evidence`要素へ変換
- `collectEvidenceStmts`(:565) — `SReturn`処理で`resolveExprType`を呼び、`ReturnSlot`とペアにして`Evidence`へ変換
- `fnDeclEvidence`(:654) — 末尾式の`resolveExprType`結果を`ReturnSlot`とペアにする

### `Evidence`

- `callEvidence`(:526) — `Call`ノードのぶんだけ生成
- `collectEvidenceStmts`(:565) — 各文の証拠を連結して蓄積、`(LocalEnv, Evidence)`で返す
- `fnDeclEvidence`(:654) — 1関数ぶんを連結
- `programEvidence`(:641) — 全関数＋暗黙mainぶんを集約（完成品の`Evidence`）
- `resolveSlots`(:695) — `Evidence`を消費し、`resolveOne`を各未解決スロットに適用
- `resolveOne`(:721) — `Evidence`から該当スロットの候補を抜き出し単一化する最終消費者

データフロー: `SlotResult`（1式の答え）→ 3箇所で`Slot`とペアの`Evidence`要素に変換 → `callEvidence`→`collectEvidenceStmts`→`fnDeclEvidence`→`programEvidence`の順に`++`で集約 → `resolveOne`が読んで終わる、という一方向フロー。`LocalEnv`だけはこの流れとは別軸で、`collectEvidenceStmts`が文を辿る間だけスコープ状態として更新される。
